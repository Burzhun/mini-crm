# Решения и допущения

1. Все постановщики имеют одинаковые права на все объекты и задачи; организация одна. Роль хранится в защищённой таблице профилей, назначается администратором. Самостоятельной регистрации и повышения роли нет.
2. Назначать можно только исполнителя. Задача без объекта или исполнителя не создаётся. Название объекта/задачи и адрес обязательны; описание задачи необязательно.
3. Исполнитель видит в карточке объекта только собственные задачи и рассчитанный по ним прогресс. Список сотрудников для него ограничен своим профилем и авторами его задач.
4. Постановщик может редактировать данные и менять исполнителя в любом статусе. Переназначение и перенос на другой объект не сбрасывают статус. Автор и дата создания неизменяемы. Назначение постановщику запрещено.
5. Начальное состояние «Новая» также попадает в историю с пустым исходным статусом. Комментарий необязателен для любого перехода, кроме «На доработке». Одни пробелы не считаются комментарием. Время хранится в UTC, отображается в часовом поясе браузера.
6. Принятая задача не открывается повторно: дополнительных переходов нет. Изменения текста и назначения не включаются в историю статусов, поскольку ТЗ требует именно смены статусов.
7. Удаление задач и объектов физическое, с подтверждением. История сохраняется, в том числе после удаления всего объекта: `task_history.task_id` хранит исходный UUID задачи без каскадного внешнего ключа. После удаления постановщики могут читать эти события через API, а исполнители их не видят. API пользователей не может вставлять, изменять или удалять события даже после удаления задачи. Восстановление удалённой задачи и отдельный экран архива не реализованы.
8. Смена статуса — одна транзакция с блокировкой строки и проверкой ожидаемого статуса. Устаревший запрос отклоняется. Обновить данные можно кнопкой в верхней панели или перезагрузкой страницы.
9. Демо отдельно от Supabase, с вымышленными данными в localStorage; это не защищённое хранилище. Продолжает работать без настроенной облачной схемы. Реальные аккаунты и демо не смешиваются.
10. В объём не включены вложения, сроки и приоритеты, уведомления, realtime-синхронизация, пагинация, восстановление пароля, управление сотрудниками и несколько компаний. При росте объёма нужно добавить серверную пагинацию: сейчас API загружает списки целиком в пределах лимита Supabase (обычно 1000 строк).

## Что требует настройки владельцем аккаунтов

Для нового проекта применить единственную миграцию `202611050001_initial.sql` и создать пользователей по README. Она сразу содержит итоговую схему со всеми правилами доступа, сохранением истории и HTTP 409 при конфликте статусов. В существующем проекте, где уже применялись три прежние миграции, дополнительных SQL-запросов не требуется. Запрет регистрации — отдельная облачная настройка Auth, она проверяется через публичный `/auth/v1/settings`. Применить SQL-миграцию одним сервисным API-ключом нельзя: нужен SQL Editor, Supabase CLI или административное подключение к PostgreSQL.

Репозиторий на личном GitHub требует подключения GitHub или авторизации CLI. Приложение опубликовано на Vercel по публичному адресу https://kontur-crm-kappa.vercel.app; повторная публикация описана в README.
