# Проверка безопасности — 5 ноября 2026

Проверены миграции, реальные Supabase Auth/REST/RPC, исходники, достижимая история Git и браузерная production-сборка. Реальный API проверялся с публичным ключом без входа, под постановщиком и под двумя исполнителями. Использованы отдельные временные объекты и задачи; после проверки они удалены, события проверки сохранены. Существующие клиентские задачи не изменялись.

| Требование                    | Результат и доказательство                                                                                                                                                                                                                                                                                                          |
| ----------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1. Ограничения на уровне базы | RLS включён на всех четырёх таблицах в миграциях. Прямые SQL- и REST-запросы отклоняют недопустимые действия независимо от интерфейса. Анонимное чтение всех таблиц запрещено.                                                                                                                                                      |
| 2. Изоляция исполнителей      | Оба реальных исполнителя видят только свои задачи, связанные объекты и доступную историю. Запрос по известному ID чужой задачи не возвращает её. Изменение, переназначение и удаление чужой задачи не выполняются. Создание задач, редактирование объектов и изменение роли запрещены.                                              |
| 3. Переходы статусов          | Клиентам запрещено напрямую менять колонку `status`. RPC и триггер проверяют пользователя и переход. Локально проверена вся матрица из 75 комбинаций. В облаке проверены запрещённые переходы, отсутствие комментария и полный допустимый цикл с доработкой. Устаревшее действие возвращает HTTP 409, без повторной записи истории. |
| 4. Неизменяемость истории     | Пользовательские API-запросы INSERT, UPDATE и DELETE отклоняются для обеих ролей. Автор и время события задаются базой. После миграции `002` удаление задачи или объекта сохраняет события с исходным ID задачи. Постановщик может их читать через API; отдельный экран архива не входит в объём приложения.                        |
| 5. Запрет регистрации         | В реальном облачном `/auth/v1/settings` подтверждено `disable_signup: true`. Прямой вызов signup публичным ключом отклонён с `signup_disabled`. Отсутствие формы регистрации на фронтенде не использовалось как доказательство.                                                                                                     |
| 6. Секретные ключи            | Секретный ключ проверен на отсутствие в отслеживаемых файлах, достижимых Git-объектах и готовой браузерной сборке. Дополнительно проверены форматы `sb_secret_…` и JWT с ролью `service_role`. Совпадений нет, `.env`-файлы не закоммичены. Во фронтенде используется только публичный ключ.                                        |

## Найдено и исправлено

1. Регистрация в облаке была открыта. Владелец отключил её, запрет повторно проверен через настройки и прямой запрос signup.
2. Удаление задачи раньше каскадно удаляло историю. Применена `202611050002_preserve_history.sql`: каскадная связь удалена, события остаются в базе и продолжают быть недоступными для изменения через API.
3. Для устаревшего статуса использовался SQLSTATE `40001`. На текущем облачном PostgREST он приводил к бесконечным повторам и зависанию запроса. Применена `202611050003_conflict_response.sql`, использующая `PT409`. Ранее зависшие запросы завершены владельцем через ограниченный maintenance-скрипт; повторная облачная проверка получила HTTP 409. [Описание причины в документации Supabase](https://supabase.com/kb/troubleshooting/high-cpu-and-infinite-transaction-retries-when-using-custom-error-codes-in-rpc-functions).

## Повторяемые проверки

- `npm run test:db`: 20 групп проверок, включая 75 комбинаций ролей/статусов, параллельные запросы и сохранность истории после удаления. Нужен `TEST_DATABASE_URL` отдельного временного PostgreSQL, как описано в README.
- `npm run audit:cloud -- --probe`: 13 групп прямых проверок реального Supabase. Нужны ключи и пароли трёх тестовых аккаунтов из `.env`. Без `--probe` выполняются только чтение настроек Auth и анонимные запросы. Подробный машинный отчёт сохраняется в игнорируемом `.local/security-cloud.json`, без ключей, паролей и токенов.
- `npm run audit:secrets`: проверяет отслеживаемые файлы, достижимую историю Git и существующий `dist`. Перед проверкой новой сборки выполнить `npm run build`.
- Сборка TypeScript/Vite, 3 теста доступных действий и 2 браузерных сценария также проходят.

Права пользователей проверялись с публичным ключом и их собственными сессиями. Сервисный ключ использовался только внутри локальных административных скриптов для контрольного чтения. Он имеет административный доступ по назначению и не относится к пользовательскому API приложения.
