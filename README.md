# Контур — мини-CRM «Объекты и задачи»

React 19 + TypeScript + Vite + Supabase Auth/PostgreSQL. Русский адаптивный интерфейс, две роли, CRUD объектов и задач, шесть разрешённых переходов статуса, обязательный комментарий к доработке и история. Авторизация по email/паролю, без формы регистрации.

## Запуск

Нужны Node.js 20+ и npm.

```sh
npm ci
cp .env.example .env.local
# Заполнить VITE_SUPABASE_URL и VITE_SUPABASE_ANON_KEY
npm run dev
```

В PowerShell вместо `cp` можно использовать `Copy-Item`. В браузере: http://127.0.0.1:5173. Для production: `npm run build`, затем разместить `dist` на статическом хостинге. `npm run preview` проверяет production-сборку локально. На Vercel/Netlify: build `npm run build`, output `dist`; добавить две публичные переменные `VITE_SUPABASE_*` перед сборкой. `.openai/hosting.json` относится к публикации через Sites и не нужен Vercel/Netlify.

## Подготовка Supabase

1. Создать проект. Выполнить целиком [миграцию](supabase/migrations/202611050001_initial.sql) в SQL Editor **пустой базы** или применить через Supabase CLI: `supabase link --project-ref <ref>` и `supabase db push`.
2. В Authentication → Sign In / Providers отключить **Allow new users to sign up**. Оставить email/password. Это отдельная настройка облачного Auth: SQL-миграция не меняет её. Для локального Supabase запрет уже указан в `supabase/config.toml`.
3. В Project Settings → API Keys скопировать **publishable/anon** key и Project URL в `.env.local`. Никогда не использовать `service_role`/`sb_secret_*` с префиксом `VITE_`.
4. Создать пользователей вручную в Authentication → Users, затем добавить профили через SQL Editor:

```sql
insert into public.profiles(id,name,role) values
 ('<UUID постановщика>','Александр Волков','manager'),
 ('<UUID исполнителя 1>','Михаил Соколов','worker'),
 ('<UUID исполнителя 2>','Анна Петрова','worker');
```

Профили и роли изменяет только администратор базы. Метаданные Auth пользователя не используются как источник роли. Постановщиков может быть несколько.

### Автоматическое заполнение тестовыми данными

Вместо ручного создания пользователей на **пустом** проекте можно запустить серверный скрипт:

```sh
cp .env.example .env
# Заполнить SUPABASE_URL, SUPABASE_SERVICE_ROLE_KEY, VITE_SUPABASE_ANON_KEY
# и три SEED_*_PASSWORD (каждый от 12 символов).
npm run seed
```

Создаст 3 пользователей, 3 объекта, 10 задач в разных статусах. История формируется настоящими переходами под соответствующими пользователями. Пароли не выводятся. Пользователи: `manager@kontur.test`, `mikhail@kontur.test`, `anna@kontur.test`; пароли — заданные вами переменные. Скрипт требует административный ключ **только локально** и не включается в браузерную сборку. При существующих объектах/аккаунтах останавливается, не сбрасывает пароли; при частичной ошибке нужно проверить уже созданные записи вручную. Не запускать повторно вслепую.

## Демо

Кнопки на экране входа открывают отдельный локальный деморежим: постановщик и два исполнителя, три объекта и десять задач. Данные хранятся в localStorage этого браузера. Смена роли доступна в верхней плашке. Демо не использует облачную базу, не предназначено для реальных данных и **не доказывает безопасность**. Демоаккаунты не создают пользователей Supabase. Чтобы сбросить демо, удалить ключ `kontur-data` из localStorage.

## Безопасность

- RLS на всех четырёх таблицах. Исполнитель читает только назначенные задачи и связанные объекты. В общей карточке объекта он также видит только свои задачи. Другие исполнители и несвязанные постановщики ему не раскрываются.
- У клиентов нет прав менять профили/роли, идентификатор задачи, автора, дату создания или колонку статуса. Только постановщики редактируют содержание и назначения.
- `change_task_status` блокирует строку `FOR UPDATE`, проверяет ожидаемый статус и доступ; триггер проверяет разрешённый переход и обязательный комментарий. Параллельное устаревшее действие получает ошибку, а не перезаписывает результат.
- История пишется триггером в той же транзакции. Через API разрешён только SELECT: нельзя подделать автора, время, вставить, исправить или удалить отдельную запись. Удаление задачи постановщиком каскадно удаляет её историю — это явное решение задания.
- Все `SECURITY DEFINER` функции используют пустой `search_path` и полные имена таблиц. Функции-триггеры недоступны для вызова API; вспомогательная функция роли находится в неэкспонируемой схеме `private`.
- Анонимные пользователи не имеют доступа к таблицам. Секретов в исходниках нет. `.env*` игнорируются, кроме шаблона. Публичный ключ допустим во фронтенде; защиту обеспечивают права базы и Auth.

Архитектура соответствует документации Supabase: [RLS](https://supabase.com/docs/guides/database/postgres/row-level-security), [функции базы](https://supabase.com/docs/guides/database/functions).

## Проверки

```sh
npm test                # 3 теста матрицы доступных действий
npm run build           # TypeScript + production-сборка
npx playwright install chromium
npm run test:e2e        # полный цикл по ролям + мобильный экран
```

Интеграционные тесты миграции требуют **отдельного временного PostgreSQL**, административного подключения с правом CREATE DATABASE/ROLE. Скрипт создаёт случайную временную БД, подменяет только инфраструктуру `auth.uid()`/`auth.users`, применяет настоящую миграцию и выполняет прямые запросы под `anon`/`authenticated`. Supabase Auth и REST этим тестом не проверяются.

```sh
TEST_DATABASE_URL=postgresql://postgres@127.0.0.1:55439/postgres npm run test:db
# PowerShell:
# $env:TEST_DATABASE_URL='postgresql://postgres@127.0.0.1:55439/postgres'
# npm run test:db
```

Проверки: изоляция задач/объектов/истории, несколько постановщиков, запрещённые записи, подмена ролей/автора/даты, вся матрица 75 комбинаций «роль × исходный статус × целевой статус», обязательный комментарий, атомарность истории, каскадное удаление. Тестовая база удаляется в конце. Недостающие глобальные роли `anon`, `authenticated`, `service_role` создаются в тестовом кластере, поэтому не использовать рабочий кластер.

## Структура

- `src/App.tsx`: точка сборки приложения — провайдер авторизации и выбор экрана.
- `src/components`: отдельные компоненты авторизации, рабочего пространства, объектов, задач, форм, диалогов и общих элементов интерфейса.
- `src/hooks`: авторизация, загрузка и изменение данных, навигация и сборка состояния рабочего пространства.
- `src/contexts`: контексты авторизации и рабочего пространства.
- `src/utils`, `src/types`: фильтрация списков, вспомогательные функции и типы состояния интерфейса.
- `src/styles.css`: стили интерфейса.
- `src/domain.ts`: типы и доступные действия интерфейса.
- `src/api.ts`: Supabase и изолированный demo-адаптер.
- `supabase/migrations`: окончательные правила безопасности и схема.
- `scripts/seed.mjs`: административное заполнение.
- `scripts/test-db.mjs`, `e2e`: проверки доступа и пользовательских сценариев.
